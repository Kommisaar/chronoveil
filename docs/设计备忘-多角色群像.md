## 1. 现状盘点（代码事实）

### 1.1 数据层

- **characters 表**：纯单角色卡（persona / render_style / model_config / calendar_config），
  `migrations/0001_init.sql:11-23` + 0003/0005/0006 增列；无任何「组合 / 群像」概念。
- **sessions ↔ 角色是单角色硬绑定**：`sessions.character_id INTEGER NOT NULL REFERENCES
  characters(id)`（`0001_init.sql:27`）；全库**不存在 roster 关联表**。领域侧
  `Session.character_id`（`domain/models.rs:72`）。建会话入参 `NewSession` 只有单
  `character_id` + `opening`（`models.rs:175-183`），`OpeningSeed`（`models.rs:160-172`）
  亦无 roster 字段。
- **scenes.present 已是 JSON 数组**：`present TEXT  -- JSON：在场 character id 数组`
  （`0002_scenes_character_state.sql:22`；概念 §7.7 :463 同形）；读写经
  `parse_present` / `serialize_present`（`infra/storage/scenes.rs:12-23`，坏 JSON 上抛
  不吞）；存储往返测试已用**多元素数组** `vec![1, 2]`（`scenes.rs:170,185`）。落库来源
  两处：开场锚行 `present = vec![new.character_id]`（`infra/storage/sessions.rs:98`）、
  结算 `present = verdict.present.clone()`（`services/director.rs:428`）——两处 v1 均恒
  单元素（见 1.3）。
- **character_state 唯一约束天然多角色**：`UNIQUE(character_id, session_id, "key")
  WHERE deleted_at IS NULL`（`0002:39-40`）；领域注释明说「状态属于这个会话里的这个
  角色」（`models.rs:274-294`）；upsert 按三元组覆盖（`infra/storage/character_states.rs:47-90`）。
  同会话挂 N 个角色的状态，**数据层零迁移可用**。
- **messages.character_id 是死列**：迁移 0002 已加（`0002:44-45`，注释「读写接线随导演
  结算任务」），但至今零接线——`NewMessage` 不含该字段（`models.rs:186-195`；文件头
  `models.rs:5-6` 自述「character_id 仍只在库内」）；insert 全程不含它（SQL 八列
  `infra/storage/messages.rs:44-57`，返回 `Message` 亦无 :59-71）；读路径 COLS 也不查
  （`messages.rs:12-13`）。
  `Message` 结构体只有 `scene_id`（`models.rs:104`），无 character_id 字段。

### 1.2 装配层（services/prompt.rs + generation.rs）

- `AssembleInputs` 单角色：`character: &'a Character`（`prompt.rs:49`）——persona 单段
  注入（`prompt.rs:85-88`，注释自认是 BR-001「在场完整人设」的 v1 单角色形态，`prompt.rs:5`）。
- **状态快照全量不分角色**：`states: &'a [CharacterState]` 整会话列表直入
  （`prompt.rs:53`），渲染按 scope 分「当前状态 / 关系」两组、行形态 `- key：value`
  （`prompt.rs:244-264`，行拼装 :259）——**不区分状态属于哪个角色**，多角色下「情绪」
  无法分辨是谁的。
- **编年史不含角色维度**：远景行 = `场idx · location · time_note · date_label · summary`
  （`prompt.rs:180-217`，字段循环 :195-207）——`Scene.present` 有数据但不渲染，模型
  从 system 无从得知任何一场谁在场。
- 近景消息只映射 `role → ChatRole`（`prompt.rs:105-111`），说话人维度在装配产物中不存在。
- 读取侧同样是「会话→角色」单取：`get_character(session.character_id)`（`services/generation.rs:371`）、
  `list_character_states(session_id)` 全量（`generation.rs:379`）、装配（`generation.rs:419-426`）。
- 落库侧 `NewMessage` 无 character_id（`generation.rs:437-445` 构造处）。

### 1.3 结算层（services/director.rs）

- 裁决 schema 本身是**多角色形态**：`DirectorVerdict { present: Vec<i64>, states:
  Vec<StateOp> }`（`director.rs:66-80`），`StateOp::Upsert/Clear` 均带 `character_id`
  （`director.rs:84-100`）。
- **present 被 v1 收窄覆盖**：`normalize` 输出 `present: roster.to_vec()`——模型给的
  present 仅作占位、校验不扩展（`director.rs:204`，收窄注释 :135-137）；roster 在编排层
  恒为 `vec![(character.id, character.name)]` 单元素（`director.rs:510`，注释 :509）。
- **states 的 character_id 已做 roster 校验**：roster 外的 upsert / clear 丢条继续
  （`director.rs:160-162, 185-187`）。但 v1 roster 只有会话角色一人，所以「存在性 +
  在场性」校验实际退化为恒等检查；`build_write` 直接信任 normalize 后的 id 构造
  `NewCharacterState`（`director.rs:435-447`），clear 按 (character_id, key) 映射在世行
  id（`director.rs:449-458`）——多角色泛化时这套「roster 交集过滤」骨架可直接沿用。
- 结算 prompt 的 payload 已带 id 维度：状态集行 `[id] scope key = value (expiry)`
  （`director.rs:309-328`，有 id 无**名字**）；在场名单 `[id] name`（`director.rs:330-337`）。
  叙事窗口只有 `[user]/[assistant]` 前缀（`director.rs:376-386`），单角色叙述体。
- `SettlementWrite` / `AttachRange` 无角色维度：消息归属按消息 id 半开区间整段挂场景行
  （`domain/ports.rs:20-24, 38-54`）——群像下「这一段是谁说的」与「归属哪一场」正交，
  归属机制本身不需要动。
- 触发与结算粒度：单条 assistant 命中场景线结算一次（`director.rs:36-54`），无
  enter/exit 字段（概念 §7.2 :355-367 的 enter/exit 未实现，被 present 收窄吸收）。

### 1.4 探索层（services/explorer.rs）

- 全链路**零角色维度**：`explore` 签名无角色参数（`explorer.rs:80-88`）；工具面仅
  `search_history(keyword)` / `read_scene(scene)`（`explorer.rs:214-242`）；引文与整场
  输出格式均为 `[场N] [role] 原文`（`explorer.rs:309, 357-359`）——多角色下「[assistant]」
  无法回答「林晚上次说什么」。研究员 system 亦是单角色叙事假定（`explorer.rs:57-69`）。

### 1.5 wire 层与前端

- **wire 已透传角色维度（无人消费）**：`SceneDto.present: Vec<i64>`（`interfaces/ipc.rs:407`，
  TS `bindings.ts:450`）、`CharacterStateDto.character_id`（`ipc.rs:434`）；
  `list_scenes` / `list_character_states` 命令均已存在。空数组透传有测试
  （`ipc.rs:1680-1688`）。
- **ChatMessage.characterId 是派生值不是事实值**：wire 带 `character_id: Option<i64>`
  （`ipc.rs:196`），但注释明说「messages 表不冗余存说话人」（`ipc.rs:189-190`）——
  `list_messages_impl` 把**所有** assistant 消息标成 `session.character_id`
  （`ipc.rs:710-725`，match :718-721）。会话单角色时恒真；多角色即错。
- 流式事件路由键为 (session_id, message_id)，无角色（`interfaces/events.rs:31-89`）——
  「每拍一条消息」的事件模型对群像原语天然够用。
- 前端历史消息渲染**已按消息级 characterId 查名**：`speakerOf` 用
  `characters.get(message.characterId)?.name`（`features/chat/ChatView.tsx:392-395`）——
  后端一旦给真值，历史渲染零改动。
- **流式行硬绑定会话角色**：说话人 = `sessions.find(...).characterId`（`ChatView.tsx:397-400`），
  演出 tuning 的 renderStyle 亦取会话角色单一值（`ChatView.tsx:401-406`）；
  `StreamingMessage` 的 speaker 是单字符串 prop（`StreamingMessage.tsx:78, 252`）。
- **账本面板不显示归属**：状态按 scope 两组渲染 `key：value`（`ledgerPanel.tsx:157-175,
  228-229`），场景行不渲染 present（`ledgerPanel.tsx:272-305`）——多角色数据到了前端
  也没有出口。
- **EnsemblePanel 是 null 占位**（`features/ensemble/EnsemblePanel.tsx:1-7`，注释挂
  UC-002 / FR-010 / ADR-006 三入口与 manual 锁）。会话清单仍以 `stores/ui.ts` 的
  `refreshSessions` 单点重拉（`src/stores/ui.ts:34,62`），SessionSummary 单 character_id
  （`ipc.rs:121-126`）；角色页 session_count 按其统计（`ipc.rs:927`）。

## 2. 缺口清单（v1 → 群像，按层级分级）

**A. 数据层已就绪（零迁移 / 近零迁移）**

1. character_state 三元组唯一约束天然多角色（`0002:39-40`）；
2. scenes.present JSON 数组、解析 / 序列化 / 往返测试齐备（`scenes.rs:12-23,170,185`）；
3. messages.character_id 列已存在（`0002:45`）——缺的只是读写接线（归 C）。

**B. 服务层需泛化（改造而非新建）**

1. 结算 roster 来源：`director.rs:510` 单元素 → 注册表查询；
2. 装配多 persona：`AssembleInputs.character`（`prompt.rs:49`）→ 在场全卡 + 不在场
   一行带过（概念 §7.3 :369-375）；状态快照分组加角色维度（`prompt.rs:244-264`）；
   编年史行加在场列（`prompt.rs:195-207`）；
3. present 校验语义：恒等 roster（`director.rs:204`）→ roster 交集校验后透传模型值；
4. explorer 工具 / 引文格式加说话人维度（`explorer.rs:214-242, 309, 357-359`）；
5. 结算 prompt 状态集行补角色名（`director.rs:309-328`）。

**C. wire / 存储层需扩展**

1. messages.character_id 全链路接线：`NewMessage`（`models.rs:186-195`）→ insert
   （`messages.rs:43-72`）→ 读 COLS（`messages.rs:12-13`）→ wire 改「列值优先、
   派生兜底」（`ipc.rs:710-725`）；
2. roster 居所：新关联表（如 session_member）或等价物 + 迁移；`NewSession` /
   `OpeningSeed` 加 roster 入参（`models.rs:160-183`）；create_session 扩参
   （`ipc.rs:628-637`）；
3. SessionSummary / CharacterSummary 是否带 roster（`ipc.rs:121-126, 143-169`）；
4. 生成原语「以角色 X 生成下一条消息」：`GenerationTicket` 只有 session_id
   （`generation.rs:73-78`），需扩 actor 参数（命令层传参亦可，不必改 ticket）。

**D. UI 需重做 / 落地**

1. 流式行说话人与 renderStyle 按拍角色（`ChatView.tsx:397-406`）；
2. EnsemblePanel 从 null 落地为在场 chips + 点将 / 继续 / 自动三入口

## 3. 泛化路径草案（建议切片顺序）

前提拍板见 §4-Q1：若走概念 §7.4 的「以角色 X 生成」原语路线，装配函数可基本复用
（单 persona 每拍重注入，人设漂移防法即概念 :396），改造重心在 roster 与原语接线；
若走「单次生成多角色台词」路线，装配与消息归属都要大改。以下按原语路线排刀。

| 切片 | 内容 | 主要文件 | 风险 | 验收要点 |
|---|---|---|---|---|
| 1 | **同会话多角色注册**：session_member 迁移 + `NewSession` 扩 roster（上限拍板 §4-Q4）+ create_session 扩参 + wire；`sessions.character_id` 保留为「主持人 / 主角」兼容旧语义（§4-Q3） | `migrations/`、`models.rs`、`storage/sessions.rs`、`ipc.rs` | 低（纯增量，旧会话零感知） | 旧数据回归全绿；roster 往返；check:ipc / whitelist 零意外 |
| 2 | **装配多 persona 注入**：`AssembleInputs` 增 roster 角色列表；在场全卡、不在场一行；状态快照 / 编年史加角色维度 | `services/prompt.rs` | 中（system 长度膨胀，见 §4-R1） | prompt.rs 离线单测锁新形态；单角色会话产物逐字节兼容 |
| 3 | **消息说话人接线**：character_id 列读写打通，wire 列值优先、派生兜底；存量 NULL 回退策略（§4-Q6） | `models.rs`、`storage/messages.rs`、`ipc.rs` | 低-中（触碰消息主链路） | 新消息落库带真值；旧会话渲染不变；前端历史渲染零改动即受益（`ChatView.tsx:394` 已就绪） |
| 4 | **结算多角色**：roster 泛化 + present 交集校验透传 + （拍板后）enter/exit 字段；不在场角色状态冻结语义（§4-Q2） | `services/director.rs` | 中（模型幻觉 id——已有 roster 过滤兜底，`director.rs:160-162`） | 多角色状态 upsert/clear 落库正确；present 变化可读；单角色行为不回归 |
| 5 | **「以角色 X 生成」原语 + UI**：命令扩 actor；流式行 speaker / renderStyle 按拍；EnsemblePanel 三入口；ledgerPanel 分组 | `ipc.rs`、`generation.rs`、`ChatView.tsx`、`EnsemblePanel.tsx`、`ledgerPanel.tsx`、i18n | 高（生成互斥 / regenerate「重掷谁」/ 自动模式停止条件） | 同会话互斥不破（`generation.rs:100` 注册表按 session）；流式事件无需改动（路由键本就不含角色）；继续 / 自动可打断 |

顺序理由：1→2 让「模型知道有谁在场」先行（纯 prompt 工程、无行为风险）；3 独立于 2/4
可并行；4 依赖 1 的 roster 与 3 的说话人列（结算叙事窗口将来可标说话人）；5 收口 UI。
每片独立可合并，单片回滚不伤账本（scenes / character_state 语义未动）。

## 4. 风险与开放问题（需用户拍板）

**决策类**

- **Q1 生成模式**：群像台词走「LLM 单次生成多角色整段（一条 assistant 内多角色对话，
  messages.character_id 无法逐句归属）」还是概念 §7.4 原语「每角色独立生成一条」？
  决定切片 2/3/5 形态。**建议：原语路线**（概念文档既定，管线改动最小）。
- **Q2 不在场角色的状态**：present 变动后，离场角色的 scene_end 状态是否照常清算、
  还是冻结至回归？影响 normalize 与 expiry 语义。**建议 v1 照常清算**（遗忘 = 不再
  注入，概念 :414）。
- **Q3 sessions.character_id 的去留**：保留为「主角 / 主持人」双轨，还是彻底 roster 化？
  涉及角色页 session_count（`ipc.rs:927`）与侧栏命名（`Sidebar.tsx:289`）等既有读方。
  **建议：保留兼容**。
- **Q4 roster 上限与准入**：同会话角色数上限（prompt 预算硬约束）；会话中途能否加人 /
  退人（v1 建议仅建会话时定死）。
- **Q5 「你」的人称**：多角色下 relation scope 的「对你」语义是否仍指单一用户人称
  （建议是）；角色间关系是否要拆键（「A 对 B」），键名约定谁来定。
- **Q6 存量消息回填**：character_id 为 NULL 的历史消息按会话主角回填，还是保持 NULL
  显示「—」（`ChatView.tsx:394` 现状即回退「—」）。**建议：不回填，保持可辨的 NULL**。

**风险类**

- **R1 system 预算**：每个在场角色完整 persona 进 prompt，多角色线性膨胀；近景预算
  （`NEAR_VIEW_CHAR_BUDGET`）只管消息侧，persona 侧无预算机制，需要上限或摘要策略。
- **R2 说话人混淆**：原语路线下单拍单角色、混淆风险低；但结算叙事窗口仍是
  `[user]/[assistant]` 裸前缀（`director.rs:376-386`），多角色下裁决质量依赖切片 3/4
  把说话人带进窗口。
- **R3 regenerate / 结算欠账语义叠加**：重掷某角色的消息撞已结算边界时，既有已知限制
  （`generation.rs:452-453` 注释）在多角色下不变但更难解释。
- **R4 演出归属**：render_style / accent_color / 头像按拍角色切换，`StreamingMessage`
  的单一 tuning prop（`ChatView.tsx:401-406`）需要参数化；出场动画与角色切换的视觉
  连续性待设计。
- **R5 自动模式失控面**：连续生成 + 结算阻塞（ADR-005 线性阻塞）叠加，单拍耗时放大；
  停止条件（轮数 / 消极拍判定）需要导演裁决支持，属概念 §7.4 未落地的第二原语。

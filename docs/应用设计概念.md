## 0. 项目定位与铁律

- **个人自用，不发布**。不迁就市面产品的交互习惯，一切以自己的使用体验为准。
- **一切数据本地化**：聊天记录、人设卡、（将来的）克隆音色素材只存本机，不上传任何服务器。
  动机之一是版权——"这种东西肯定只会存在自己的电脑上啦，传到网络上有版权问题"。
- **渲染层天然无外链**：markdown-lite 子集刻意不含链接、图片（见 §4），页面永远不会向外部发请求。
- **TTS 是长期展望**，当前不做；留缝不留壳（见 §9）。

## 1. 技术栈与架构

| 层 | 选型 |
|---|---|
| 壳 | Tauri 2（桌面单机应用） |
| 后端 | Rust：`model.rs`（LLM 调用）+ `db.rs`（SQLite） |
| 前端 | React + Vite + TypeScript |
| 数据 | SQLite 单文件，rusqlite + 手写迁移，存于应用数据目录 |

数据流（单向）：

```
LLM API ──SSE──▶ model.rs ──emit──▶ Tauri 事件通道 ──▶ 前端缓冲队列 ──▶ 渲染引擎 ──▶ DOM
                     │                                      ▲
                     └──────────▶ db.rs 落库（原始文本）      └─ render_style 读自 Agent
```

事件通道是**类型化**的：`token` / `reasoning` / `done` / `error`（将来可扩 `audio`）。

## 2. 流式渲染引擎（核心设计）

### 2.1 为什么需要缓冲

SSE 返回的字符是**一阵一阵**到达的（网络突发），直接渲染就是一顿一顿的"卡顿感"。
缓冲层把**到达时间**和**显示时间**解耦：

- 显示永不跑赢网络（没到就是不显示）；
- 网络的抖动不传导给眼睛（到了先攒着，匀速放行）；
- 代价是延迟，但延迟**有界且自收敛**：延迟 ≈ 积压量 ÷ 追速，追速自适应（§2.4）。

对比传统方案：固定延迟线（人为加一个固定延迟换平滑）延迟恒定但平均更高；
本方案平时几乎零延迟，只有积压时才产生延迟并自动收敛。

### 2.2 三段式结构

```
生产者（SSE onChunk / demo 里是网络模拟器）
   → 队列 queue（字符级 + 结构单元）
     → 消费者（16ms 固定 tick，按信用节拍吐字）
```

- **生产者**只管把到达的字符推进队列，不做任何渲染决策。
- **队列**里有两类单元：文本单元 `{t, a, b}`（a=动作标记，b=加粗标记）和
  结构单元 `{para:true}` / `{hr:true}`（段落切分 / 场景线，**原子不可拆**）。
- **消费者**是唯一的渲染出口，所有节奏决策都在这里。

### 2.3 信用机制（防漂移的节拍器）

不用"每个字一个 setTimeout"的链式调度（误差累积、卡顿后突然喷字），而是固定 16ms tick + 信用记账：

```
credit += dt / interval          // 每帧按流逝时间攒信用
while (credit >= 1 && queue.length) {
    吐出一个单元; credit -= 1
    若有微停 p: credit -= p / interval   // 微停 = 负信用，不是 sleep
}
credit = min(credit, 3)          // 上限 3，防burst
空队列时 credit = 0               // 空转不攒速度
```

实现时踩过并规避的三个坑：
1. **setTimeout 链漂移**：逐字 setTimeout 误差累积，节奏越走越歪 → 固定 tick + 信用；
2. **空转攒速**：队列空时若信用继续累积，网络一来就瞬间喷出 → 空队列清零；
3. **无界积压**：网络长卡顿后延迟越滚越大 → 自适应追速兜底（下一节）。

### 2.4 自适应追速

```
k      = max(0.25, 1 / (1 + backlog / 45))
interval = max(10ms, 节奏基准 × k)
```

- 积压 45 字 → 吐字速度 ×2；积压越大越快，**封顶 ×4**（k 下限 0.25）；
- 追平后 k 回到 1，速度自然回落到基准——"欠了债加班还，还完就下班"。
- `节奏`（用户可调，10–160ms，默认 45ms/字 ≈ 22 字/秒）是**基准值不是定值**，
  实际吐字速度 = 节奏 × 当时的加速因子。

三个速度概念的关系（对话中多次澄清）：
**API 实际输出速度**（生产端，不可控）≠ **节奏**（消费端基准）；
**抖动**只影响"数据什么时候到"；最终观感 = 节奏 × 自适应 × 网络供给的交集。

### 2.5 标点微停（呼吸感）

微停通过负信用实现（`credit -= p / interval`），不阻塞 tick：

| 触发 | 停顿 |
|---|---|
| 段落 / 场景线 | 260ms + 节奏 |
| 句末（。！？…） | 150ms + 节奏 × 0.8 |
| 逗号（，、；：等） | 55ms + 节奏 × 0.4 |

设计原则：轻微的呼吸感，**不是**打字机式的大停顿。有开关（标点微停）。

### 2.6 粒度

发射单元的字数：1（逐字）/ 2（逐词，默认）/ 4（成块）。`takeUnit()` 会把
队列头部**相同标记（a/b）**的相邻字符合并成一个单元直到达到粒度上限；
结构单元永远单独出队。

### 2.7 网络抖动模型（demo 模拟器，真实 App 无此部件）

滑条 j ∈ [0,100]：

- 卡顿概率 `j × 0.30`；卡顿时长 `400 + j×900 + rand×600` ms；
- 平时包间隔 `(50 + j×50) ~ (90 + j×220)` ms；
- **卡顿后连珠炮**：2–4 个包以 15–45ms 紧急补发——模拟 TCP 积压一次性送达；
- 每包 2–7 字；首包延迟 300ms（dots 风格 1150ms，配合加载点）。

验证结论：抖动 0 时零等待全程 3.9s；抖动 100 时 62% 时间在等网络。
缓冲模式下积压稳定在 2–6 字、卡顿后以约 60 字/秒追平；
直出模式下每次 +8~18 字跳进、伴随 2.4s 级冻结。

### 2.8 动画遮盖原理

长时长的 CSS transition 相互重叠，可以**桥接发射间隙**：第 N 个字还在渐入时，
第 N+1 个字已经出场，视觉上感知不到队列的间歇。实测 direct 模式 + 800ms 动效
即可在截面上看到透明度梯度分层。这是"动画可以慢一点，遮盖卡顿"的机制基础。

### 2.9 与真实应用的映射

- SSE `onChunk` → `queue.push(...)`（生产者一行代码）；
- 消费者用 `setInterval(tick, 16)` 或 rAF 驱动，逻辑不变；
- React 组件层只负责插 `<span class="tok">`，动画全部交给 CSS；
- `render_style` 是 Agent（角色卡）的实例字段，每个角色可以有自己的出场方式。

### 2.10 踩坑记录（CSS/DOM）

- **transform 对 inline 元素无效**：所有带位移/旋转/缩放的风格必须 `display:inline-block`；
- 双 rAF（`requestAnimationFrame` 嵌套两层）后再加 `.show`，确保初始帧先渲染；
- 中途切换风格：改 `data-anim` 即时生效，不必重播（demo 支持流式中途切换）。

## 3. 动画体系（18 种）

时长基准 `--dur`：150–1200ms 可调（默认 450ms），滑条实时生效；
每种风格有独立倍率。全程 CSS 驱动（除 decode 的乱码轮换由 JS 驱动）。

| # | 风格 | 机制 | 倍率 |
|---|---|---|---|
| 1 | 平滑浮现 · ChatGPT 系 | 成块淡入 | ×1.0 |
| 2 | 光标随行 · Claude 系 | 快速淡入 ×0.45 + 常驻闪烁光标 | ×0.45 |
| 3 | 打字机 · 经典 | 无动画，节奏全靠引擎 | — |
| 4 | 浮现上移 | 淡入 + 上浮 0.35em | ×1.3 |
| 5 | 聚焦显影 | blur 6px→0 | ×1.5 |
| 6 | 思考点 + 平滑 · 国产系 | 首字前三点加载，正文同 fade | ×1.0 |
| 7 | 霓虹通电 · 赛博 | 灯管闪烁几轮(steps)后稳亮 | ×1.4 |
| 8 | 字符解码 · 黑客 | 片假名/数字乱码轮换 7–12 轮 @42ms 后定格 | JS 驱动 |
| 9 | 翻牌登场 · 翻牌 | rotateX(-92°) 绕底边翻立，微过冲 | ×0.8 |
| 10 | 坠落弹跳 · 落石 | 从上坠落 + 回弹曲线 | ×0.95 |
| 11 | 光束扫描 · 扫描仪 | clip-path 从左揭示 + 辉光扫过褪去 | ×1.1 |
| 12 | 墨晕沉淀 · 水墨 | scale1.5 + blur5px 淡影收束成字 | ×1.3 |
| 13 | 信号撕裂 · Glitch | RGB 双色 text-shadow 分离抖动后归位 | ×0.9 |
| 14 | 笔迹生长 · 书写 | scaleX(0→1) 从左被"写"出来 | ×0.75 |
| 15 | 星尘落定 · 尘埃 | 每字从随机方向/旋转飘落归位 | ×1.1 |
| 16 | 心跳脉冲 · 悸动 | lub-dub 双跳（scale 双峰） | ×1.6 |
| 17 | 收拢凝字 · 凝聚 | letter-spacing 0.45em→0 + 微糊散去 | ×0.9 |
| 18 | 聚光点亮 · 舞台 | 暗场灰褐 #5d5a52 瞬间可见 → 琥珀辉光亮起再褪 → 字色 1.2×dur 缓升温 | ×1.6 |

补充机制：

- **随机落点属性**：每个 token 生成时注入 `--dx/--dy/--rot` 随机自定义属性，
  有风格（星尘）消费它们，其余风格无视——零成本的前置投资。
- **风格 18 的教训**：最初用 `brightness(.15)→1` 做"点亮"，但近黑气泡上 0.15 亮度的
  浅灰字 ≈ 隐形，观感退化为普通淡入（用户指出）。修复后的原则：
  **"从暗开始"的暗必须可见**——用可见的暗色（灰褐轮廓）而不是看不见的暗。
- decode 风格的乱码轮换必须登记到全局 `scrambles`，中断/重播时统一收尾定格。

## 4. Markdown-lite 流式渲染

### 4.1 子集与取舍

支持：`*斜体*`（动作）、`**加粗**`（强调）、空行分段、`---` 场景线。

刻意**不支持**：表格、链接、图片。理由：
1. 流式渲染会长时间处于"半语法"状态，复杂结构在半途必然错乱；
2. 链接/图片 = 外部请求，违背本地化铁律，禁掉最干净；
3. TTS 朗读时需要剥掉语法，子集越小剥离越可靠。

### 4.2 段落封存（混合渲染）

流式中同时存在两种渲染态：
- **已完成段落**：封存（sealed）为静态容器，不再被尾部流式追加影响；
- **尾段**：token 级流式追加，光标/动画只发生在尾段。

结构单元（`{para}` / `{hr}`）在队列里作为**原子单元**流动，出队时触发封存
（`paraEl = null`，后续字符进新容器）并携带自己的深呼吸停顿（§2.5）。

### 4.3 渲染与存储分离

- **数据库永远存原始 markdown 文本**；
- 渲染发生在显示时刻（重开窗口、切会话、换风格都能重渲）；
- TTS 将来复用同一份"剥语法"逻辑得到纯朗读文本。

渲染类：`.tok.action`（斜体蓝灰 #93a5c8）、`.tok.bold`（粗、米白）、`hr.scene`
（渐变线 + ✦ 居中饰符）。

## 5. 思考双通道（reasoning block）

### 5.1 设计原则：思考走缓冲，但不走「节奏」

「节奏」服务的目标是**表演**（正文是演出，慢速打字机有审美价值）；
思考 block 是**后台**——用户在"等正片"。若思考也按 45ms/字吐，
模型 3 秒想完的内容要 15 秒才显示完，感知等待凭空 ×5，审美收益为零。
**慢动画遮盖卡顿的逻辑对思考不成立**（用户本来就接受"它在忙"）。

因此：两条通道，两种策略——思考通道约 10 倍速快滚，暗色小字；
正文通道走完整的缓冲 + 动画仪式。收拢 → 开演的反差反而强化正文的登场感。

### 5.2 阶段时序（demo 实测参数）

| 阶段 | 时长 | 内容 |
|---|---|---|
| 起 | 420–680ms 随机 | 思考盒出现，头部：呼吸点 + 流光"思考中"贴士 + 计时 |
| 快滚 | ~24ms/跳 × 2–4 字（≈10× 正文速度） | 暗灰小字流式，实时计时 |
| 落定 | 380ms 停半拍 | 思考结束的"呼吸感" |
| 收拢 | 450ms max-height 过渡 | 折叠成一行胶囊：「已深度思考 · Ns ▾」 |
| 开演 | +520ms | 正文生产者启动，从零开始 |

- **贴士轮换**（THINK_TIPS 池，12 条，随时可扩充）：乱序出发、转完一圈前不重样，
  1200ms 一换，换词走 300ms 渐出 → 换字 → 300ms 渐入。
  过程搞怪（"正在和另一个自己吵架……"），落点正经（定格文案固定为「已深度思考」）。
- **收拢后可点击回看**：胶囊有淡底/悬停提亮，点击展开/收起。
- **竞态闸门（settled）**：收拢若撞上换词的 300ms 渐出窗口，迟到的换词回调会
  覆盖定格文案或让它停在透明态 → 收拢时先落闸（`settled = true`）+
  把透明度拉回 1 兜底。

### 5.3 可见时长计时

教训：挂钟计时会把标签页切走时被浏览器节流的时间也算进去，
回来就定格出「已深度思考 · 45.4s」这种虚胖时长。修复：

- 计时**只累计页面可见的时长**（`visMs`）：每个计步点检查 `document.hidden`，
  后台流逝的时间一分不加；
- `visibilitychange` 回前台瞬间重置起算点（消除节流期间的残余误差）；
- 秒数分级格式 `fmtDur`：<10s 一位小数（3.5s）→ ≥10s 取整（45s）→ ≥60s 走 m:ss（1:23）。

理由：那是**用户感知到的等待**，不是机器的等待。App 里同理
（最小化、切会话、锁屏都不计时）。

### 5.4 生产端：两种 API 形态

- 有的 API 把推理内容放在独立的 `reasoning_content` 字段——干净，直接路由到思考通道；
- 有的内联 `<think>...</think>` 混在 `content` 里——需要流式标签切分状态机，
  并处理**半标签跨包**（`<thi` 和 `ink>` 分在两个 chunk 到达：
  尾巴攒着，判不出是否标签就不能渲染）。

### 5.5 回合代号（runId）

思考/正文有跨阶段的异步回调链（初始延迟 → 轮换 → 落定 → 收拢 → 开演）。
每次 replay 递增 `runId`，所有回调先核对代号——中途重播/切风格时，
旧回合的回调因代号失配而作废，杜绝"两路正文叠着跑"的僵尸现场。

## 6. 数据库设计（db.rs）

> 表结构是对话决策的具体化（字段名可在开工时再确认）；
> 加粗的决策是对话中明确定过的。

设计铁律：
- **本地单文件 SQLite**，存于应用数据目录，无任何网络同步；
- **存原始 markdown 文本**，渲染在显示时刻（§4.3）；
- **reasoning 单独字段落库**，与正文分离（TTS/导出/重渲不用回头剥）；
- **voice_config 是 TTS 预留缝**：可空 JSON，现在永远 null，将来只填内容不改表。

```sql
-- 角色卡
CREATE TABLE agents (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  name         TEXT NOT NULL,              -- 显示名（如"林晚"）
  persona      TEXT NOT NULL,              -- 人设系统提示词
  greeting     TEXT,                       -- 开场白（markdown-lite）
  render_style TEXT NOT NULL DEFAULT 'fade', -- 18 种风格之一（§3）
  model_config TEXT,       -- JSON：该角色专属模型覆写（provider/model/temperature…）
  voice_config TEXT,       -- JSON：TTS 预留缝，当前恒为 NULL（§9）
  created_at   INTEGER NOT NULL,
  updated_at   INTEGER NOT NULL
);

-- 会话
CREATE TABLE sessions (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  agent_id   INTEGER NOT NULL REFERENCES agents(id) ON DELETE CASCADE,
  title      TEXT,                        -- 缺省取首条用户消息截断
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL             -- 每条新消息刷新，用于会话列表排序
);

-- 消息
CREATE TABLE messages (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id INTEGER NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  role       TEXT NOT NULL CHECK (role IN ('user','assistant')),
  content    TEXT NOT NULL,               -- 原始 markdown-lite，渲染时才解析
  reasoning  TEXT,                        -- 思考内容，与正文分离落库（§5）
  think_ms   INTEGER,                     -- 思考可见时长（回看时展示"已深度思考 · Ns"）
  tokens     INTEGER,                     -- 用量统计（可选）
  created_at INTEGER NOT NULL
);

CREATE INDEX idx_messages_session ON messages(session_id, id);
CREATE INDEX idx_sessions_updated ON sessions(updated_at DESC);

-- 迁移
CREATE TABLE schema_version (version INTEGER NOT NULL);
```

要点说明：

1. **按 Agent 而非全局存 render_style / model_config**：每个角色有自己的出场
   动画和模型参数——这是"Agent 是一等实体"的直接体现；
2. **greeting 也是 markdown-lite**：开场白走同一套渲染管线；
3. **历史消息回看**：reasoning 折叠态从消息记录恢复（think_ms 直接回填显示）；
4. 迁移策略：手写顺序迁移 + `schema_version` 表，个人应用不需要更重的方案。

## 7. 多角色叙事：场景、状态与虚时（阶段 5+）

> 本章是多角色阶段的设计总纲。v1（单主角会话）不实现；
> `db.rs` 建表时按 §7.7 把缝留好。

### 7.1 场景是叙事产物，不是管理对象

用户不手动建场景。markdown-lite 的 `---` 场景线（渲染为 ✦ 分隔）就是结算触发器：
模型在叙事中自发写场景线 → 触发场景结算；会话开场也触发一次。
"现在算不算换了场景"由叙事自己说了算。

### 7.2 导演调用：一个廉价后台 JSON 调用干四件事

模式同思考通道（§5）：不阻塞正文流、可失败（失败沿用旧状态，天塌不下来）。
触发：会话开场 / 模型输出 `---` / 用户手动插场景线。
输入 = 最近叙事原文 + 上一场摘要 + 当前状态集；输出示例：

```json
{ "location": "旧书店 · 打烊后", "time": {"day": 2, "part": "夜"},
  "enter": [], "exit": ["苏叙"],
  "state": [
    {"who": "林晚", "clear": "别扭", "reason": "一夜过去"},
    {"who": "林晚", "set": {"持有": "诗集"}, "until": "event:交出"} ] }
```

四件事一次办完：**场景结算**（地点/时间）、**在场变更**（enter/exit）、
**状态清算**（过期判定）、**时间换算**（叙事相对时间 → 记账层，§7.6）。

### 7.3 在场规则（prompt 装配）

- **在场角色**：完整人设卡进 prompt；
- **不在场角色**：一行带过（"苏叙不在场（去了仓库）"），人设卡不进——
  模型既不替离场者说话做事，又知道世界上有这个人、重逢接得上；
- 离场/入场由叙事驱动（"*她推门走了*" → exit），导演结算捕捉；
- **用户终审**：会话顶部在场头像 chips，导演改动自动反映，手点即强制覆盖。

### 7.4 群像与「继续」：一个原语，三个入口

底层原语只有一件事：**以角色 X 的身份生成下一条消息**（普通模型调用，
prompt 装配 / 流式渲染 / 动画 / 落库全部照旧）。区别只在 X 怎么来：

| 入口 | X 从哪来 |
|---|---|
| 点将 | 你点某角色的头像 |
| 继续 ▸ | 导演判定谁该接话 |
| 自动 ▸▸ | 循环执行「继续」直到停止条件 |

- **「继续」按钮**：上一拍落地、场上无人欠回复时出现在输入框旁；
  一次点击走**一拍**（一个角色说一条）。你打字即夺拍，生成完当前那条就停；
- **自动模式停止条件**：用户打断（必须瞬时）/ 轮数上限（默认 4–6）/
  导演判定"这段戏需要用户介入了"；
- **消极拍**（"*她只是低头继续擦柜台*"）不是失败，是叙事的一部分，照常入戏；
  连续两拍消极 → 导演判停，藏起继续按钮、亮起输入框；
- 单主角会话里「继续」同样有意义：不想说话，点一下让她自己走一轮（v2 即可带上）。

人设漂移的防法很朴素：每一棒完整重注入人设 + 场景头，单条生成之间无共享隐状态。

### 7.5 人物状态：三层拆解 + 过期语义

| 层 | 内容 | 变化 | 存储 |
|---|---|---|---|
| 底版 persona | 性格/外貌/背景/价值观 | 几乎不变 | agents.persona |
| 状态 state | 情绪/健康/持有物/衣着 | 随戏变、有时效 | agent_state（scope=state） |
| 关系 relation | 对你/他角的态度、约定、知情 | 缓慢演化 | agent_state（scope=relation） |

- **状态属于"这个会话里的这个角色"**：挂 `(agent_id, session_id)`，
  重开会话不带旧案状态——底版还是她，案子不跟人走；
- **过期三种**：`scene_end`（场景级，默认）/ `event:xxx`（叙事事件撤销，导演判）/
  `manual`（用户终审，永远最高）；
- **结构化判据**：下一场还需要记得吗？需要 → 状态；不需要 → 留在滚动上下文
  自然消逝。条目宜少而有分量（≤10 条），多了导演自己也管不明白；
- **值用叙事语言不用纯数字**："态度：警惕 → 松动" 优于 "好感 37 → 52"
  （模型对数字不敏感，对措辞敏感）；
- 遗忘 = 不再注入，无需任何删除戏法。

### 7.6 虚时与虚拟日历

**双层时间**：

- **记账层**（唯一事实源）：`{day, part}`。day 单调递增、锚定会话开场那天；
  part 取粗粒度时段（清晨/上午/午后/黄昏/夜/深夜）；
- **叙事层**：模型自由书写（"次日清晨""三天后""不知过了多久"），
  导演结算时换算成记账层；模糊跳变由导演拍一个最小合理值并写下来——
  **模糊不是问题，没记下来才是问题**。

**虚拟日历** = 数字账本之上的命名皮肤，唯一要求：与 day 双射（可反查）。

```json
{ "name": "旧都历",
  "months": ["霜月","白蜡月","融雪月","雨月","长夏月","蝉鸣月",
             "风起月","收获月","雾月","炉火月","冻雨月","岁末月"],
  "days_per_month": 30,
  "day_names": ["晨露日","萤火日","潮汐日","风息日","炉边日","集日","安息日"],
  "festivals": { "白蜡月·15": "灯节", "岁末月·30": "守夜" } }
```

- 预设：现代公历 / 七曜和风 / 干支古典 / 全架空（自起名）；
- 存 `sessions.calendar_config`，默认从 Agent 继承——同世界观共享历法；
- 节日是叙事钩子：结算发现今天是灯节 → 注进场景头，模型自己会用
  （"*街上开始挂灯了*"）；
- **开局向导自动拟历**：新会话选角后，一次廉价结构化调用按角色世界观
  自动起草"世界开局包"（日历定义 + 起始日期锚 + 开场时段），卡片式预览，
  **采用 / 换一版 / 手动改**。不让用户手填 JSON。
  这是结构化后台调用的第三个用途（导演结算 / 状态清算 / 开局拟包），
  model.rs 做成通用 helper。

两条原则：**虚时只被叙事推进**（与现实挂钟零耦合，离开三天回来还是那天清晨）；
**叙事与账本冲突时账本赢**，用户终审可改。

### 7.7 数据库增量（阶段 5 迁移）

```sql
CREATE TABLE scenes (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id  INTEGER NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  idx         INTEGER NOT NULL,
  location    TEXT,
  time_note   TEXT,              -- 叙事层时间原文
  fic_day     INTEGER,           -- 记账层：第几天（会话内单调递增）
  fic_part    TEXT,              -- 记账层：时段
  date_label  TEXT,              -- 虚拟日历命名日期缓存（"白蜡月·晨露日"）
  summary     TEXT,              -- 本场一句话（远景压缩的单元）
  present     TEXT               -- JSON：在场 agent id 数组
);
ALTER TABLE messages ADD COLUMN scene_id INTEGER REFERENCES scenes(id);
ALTER TABLE messages ADD COLUMN agent_id  INTEGER REFERENCES agents(id);  -- 谁说的；用户为 NULL
ALTER TABLE sessions ADD COLUMN calendar_config TEXT;

CREATE TABLE agent_state (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  agent_id     INTEGER NOT NULL REFERENCES agents(id),
  session_id   INTEGER NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  scope        TEXT NOT NULL CHECK (scope IN ('state','relation')),
  key          TEXT NOT NULL,    -- '情绪' / '持有' / '约定' / '对用户的态度'
  value        TEXT NOT NULL,    -- 叙事语言，非数字
  expiry       TEXT,             -- JSON：scene_end / event:xxx / null
  source_scene INTEGER,
  updated_at   INTEGER NOT NULL,
  UNIQUE(agent_id, session_id, key)
);
```

历史回看：场景边界渲染为现有 ✦ 线，点开看地点/时间/在场/状态快照——视觉件全是现成的。

### 7.8 记忆压缩（白送）

场景摘要天然就是长会话的记忆机制：

```
[场景头] 白蜡月 · 晨露日 · 黄昏 · 在场：林晚
[近景]   当前场景的消息原文（最近 N 条，逐字）
[远景]   之前每场一行摘要（含 date_label）
```

旧场景压成一行，只有当前场吃全量上下文——聊一百场不糊，
无需独立的"记忆系统"，因为结算摘要的导演调用反正都要跑。

## 8. 模型层设计（model.rs）

- **多 provider**：OpenAI 兼容协议为主（可接 DeepSeek / GLM / 本地推理服务等），
  配置 = base_url + api_key + model 名；密钥只存本机；
- **SSE 解析**：reqwest + 事件流，逐 chunk 发类型化事件（`token` / `reasoning` / `done` / `error`）
  到前端；同时原文累积落库；
- **reasoning 分离**（§5.4）：字段型直接路由；内联 `<think>` 型走流式标签状态机，
  含半标签跨包缓存；
- **健壮性**：连接超时、断流重试（幂等性由"消息级重发"保证，不追片内续传）、
  可取消（用户中断生成时立刻停，已到内容保留）。

## 9. TTS 长期展望（当前不做，留缝清单）

| 缝 | 现在做什么 | 将来怎么用 |
|---|---|---|
| `voice_config` JSON 字段 | 建表时留好，恒为 NULL | 填入音色模型路径/参数，不改表 |
| 类型化事件通道 | 只定义 4 种事件 | 加 `audio` 事件即接播放队列，缓冲引擎零改动 |
| 剥语法逻辑 | 随 markdown-lite 一起实现 | TTS 复用同一份得到纯朗读文本 |

不做的事：不放静音按钮、不做"语音设置（敬请期待）"页——**死 UI 是债，缝不是**。
克隆音色素材同样遵守本地铁律。

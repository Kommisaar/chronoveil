## 1. 结算挂点：生成生命周期内的确切位置

**位置：`generate_once` 的 `StreamOutcome::Completed` 分支内，`persist_terminal`
成功之后、`sink.release()` 之前**（`src-tauri/src/services/generation.rs:396-397`，
现为 `Ok(_) => sink.release()`）。

**触发判定**：对刚落库的 assistant 正文逐行做场景线判定，规则与渲染引擎完全一致——
`/^\s*(-{3,}|={3,}|—{2,})\s*$/`（`src/engine/parser.ts:20` 的 `SCENE_LINE_RE`；注意必须
整行匹配，不能用 `contains("---")`，行内破折号不是场景线）。判定为纯函数放
director.rs（如 `contains_scene_line(&str) -> bool`），附与引擎正则对齐的测试。只命中
一道 `---` 即触发**一次**结算（v1 收窄，见 §7-4）。

**ADR-005 线性阻塞在本代码库的落地形态**——现有机制恰好逐件对应，无需新原语：

| ADR-005 语义 | 代码承载 |
|---|---|
| 结算必须成功才推进下一拍 | 结算插在 persist 与 `release()` 之间：done 事件已被 `GenerationSink` 终态闸门扣住（`generation.rs:291-296` `held_terminal`），落库+结算完成后才放行到前端 |
| 下一拍不得提前开始 | `registry.finish()` 在 `generate_once` 返回后才执行（`generation.rs:337`）；期间任何 `send_message`/`regenerate_last` 都被注册表同会话互斥拒绝（`generation.rs:100-112`、`ipc.rs:466-469`）。即「推进」= done 放行 + 槽位释放，由构造保证 |
| 失败重试直到成功 | 结算重试循环（§2），退避 + 可打断；重试期间 done 一直扣着，前端流式态自然停留在「等待」（ADR-005：与正文生成同等对待） |
| 未成功的结算无副作用（INT-003 幂等） | 结算落库走**单事务**端口方法（§3），失败回滚即无痕迹；重试从头再来 |
| 用户可打断退出等待 | 重试间隔检查 `ticket.cancel_handle().is_cancelled()`（句柄已在 `GenerationTicket`，`generation.rs:80-84`）；打断后放行 done（assistant 整条已落库，正文无损），结算欠账处理见 §7-2 |

**事件序列推演**（对照 SEQ-001 既有断言模式 `generation.rs:735-754,821-834`）：
`token… → [DONE] → assistant 行落库 → 结算（重试…）→ scenes/character_state 行落库 →
done 放行（此时事件记录器断言 scenes 已在库）→ registry.finish`。Cancelled / Err 路径
**不结算**（半条不是完整叙事，BR-006 的触发主体不存在）。`regenerate=true` 同样参与
结算（替换后的新整条才是叙事事实）。

## 2. 结算 LLM 调用设计

**调用通道**：`LlmClient::complete_json::<DirectorVerdict>`（`llm.rs:497-531`）。非流式，
天然不向聊天流泄漏 token/reasoning 事件；`LlmError::Json` 已是可判别错误（`llm.rs:107`）。
模型名经 `effective_director_model()`（跟随主模型，INT-003）；base_url/api_key 取
`active_provider()`。新建 `director::resolve_director_llm(&FileConfig) -> Result<LlmClient, String>`
——**不复用** `resolve_effective_llm`（那是 Character.model_config 覆写语义，导演调用不
做角色级覆写，见 §7-5）。到结算时点主模型必然已配置成功（否则 `send_message` 早失败），
保留防御分支即可。

**输入 prompt 结构**（装配为纯函数，system + 单条 user）：

- **system**：导演结算指令——角色定位（后台大脑，非叙事者）；四件事清单（新场景定稿 /
  收束段摘要 / 状态清算 / 时间换算）；硬规则（BR-002：值用叙事语言非数字、条目 ≤10、
  expiry 三义；BR-003：模糊时间拍最小合理值并写进 time_note；虚时只被叙事推进）；
  **只输出 JSON**。
- **user payload**（分段标注）：
  1. 上一场快照：`latest_scene` 的 location/date_label/fic_day/fic_part/summary（无则
     「本段是开场后第一段」）；
  2. 当前状态集：`list_character_states` 全量（≤10 条即 BR-002 上限，超出全给但指令要求
     精简），格式 `[id] scope key = value (expiry)`；
  3. 在场名单 roster：v1 恒为 `[{id: session.character_id, name}]`（多角色 roster 数据
     模型未落地，§7-7）；
  4. 日历提示：calendar_config 的 name / festivals 摘要 + 当前账本位（第 N 天 · part）；
  5. 本回合叙事原文：触发消息全文 + 其前 K 条消息（建议 K=6，director.rs 内常量），
     `[user]/[assistant]` 前缀，总长字符上限建议 ~6000 字、超长从最旧侧截（token 预算
     意识；`chat_payload` 不带 max_tokens/temperature，`llm.rs:321-330`，加参数列为可选
     缝，§7-8）。

**输出 JSON schema**（serde 内部类型，非 wire DTO）：

```json
{
  "location": "旧书店 · 打烊后",
  "time_note": "次日清晨",
  "fic_day": 2,
  "fic_part": "夜",
  "summary": "昨夜争执后两人无言告别",
  "present": [1],
  "states": [
    { "character_id": 1, "scope": "state", "key": "情绪", "value": "释然", "expiry": "scene_end" },
    { "character_id": 1, "clear": "别扭" }
  ]
}
```

`date_label` **不向模型索取**——它是记账层之上的命名缓存（`models.rs:233`、FR-013），
由 fiction_time 从 `(fic_day, calendar_config)` 派生（§4）。`states` 二态：
`Upsert{character_id, scope, key, value, expiry}` / `Clear{character_id, key}`
（clear → `soft_delete_character_state`，软删可还原，ADR-009）。

**容错分层**（对应 INT-003「解析失败按失败重试，不做静默降级」）：

- **结构级**：`extract_json` 失败或 serde 拒绝 → 整次失败 → 重试。
- **字段级**（值域修正，不重试）：`location/time_note/summary` 缺失 → None（列可空，
  `models.rs:226-236`）；`fic_day` 缺失 → 沿用 `latest.fic_day`（不推进）；
  `fic_day < latest.fic_day` → clamp 到 latest（BR-003 day 单调）；`fic_part` 不在六值
  （清晨/上午/午后/黄昏/夜/深夜，BR-003）→ None；`present/states` 引用 roster 外的
  character_id、scope 非法 → 丢弃该条继续（配合 system 指令与 roster 输入，发生概率低，
  不值得整次重试烧一次调用）。

**重试策略与上限**：**不设硬次数上限**（ADR-005 决策原文「重试直到成功」，其再评估条件
留给体感反馈）；退避 500ms 起 ×2 指数、封顶 8s（对齐 `RetryPolicy::default` 节奏，
`llm.rs:52-56`；注意该默认对单条流是 2 次，导演这里要自持循环，`llm.rs:496` 注释已把
循环责任划给调用方）；每次重试输入不变（幂等）；每轮间隔查 cancel；连续 3 次失败
`eprintln!` 日志（与 `generation.rs:420` 风格一致）。单次尝试有 `read_timeout`
（默认 30s，`llm.rs:81`）兜底不会永久挂起。

## 3. domain/ports 扩展点

**可直接复用**（无需改动）：`get_session` / `get_character` / `list_messages` /
`latest_scene` / `list_scenes` / `upsert_character_state` / `list_character_states` /
`soft_delete_character_state`（`ports.rs:30-71`）。LLM 侧**不新增 trait**：services 直接持
`Arc<LlmClient>`（与 `GenerationDeps.llm` 同型，`generation.rs:308-312`；services→infra::llm
边界已有 generation 先例，boundary 脚本放行）。

**需新增：一个结算落库端口方法**（单事务，这是本切片唯一的端口扩展）：

```rust
fn commit_settlement(&self, write: &SettlementWrite) -> Result<Scene, StorageError>;
```

`SettlementWrite { scene: NewScene, close_scene_id: Option<i64>, close_summary: Option<String>,
attach: Option<AttachRange>, state_upserts: Vec<NewCharacterState>, state_clears: Vec<i64> }`，
其中 `AttachRange { scene_id, after_message_id, upto_message_id }` 用于把收束段消息
`UPDATE messages SET scene_id=?`。实现于 `infra/storage.rs`，用 `unchecked_transaction`
（照 `insert_message` :148-158 / `replace_last_assistant_message` :171-190 的既有事务
模式），把「新场景行 + 上一场景 summary 回写 + 消息归属 + 状态 upsert/清除」绑成一次
提交——这是 INT-003「未成功的结算无副作用」的字面实现，也避免半结算状态。

**scenes 行语义（需要拍板，见 §7-1）**：推荐「边界快照」模型——结算产生的新行 =
`---` 之后新场景的 header（location/fic_day/fic_part/date_label/present），行 summary =
`---` 之前刚收束段的远界一句话；收束段的消息挂到**上一行**（`latest_scene`）。这与
「点开场景线看该边界之后的地点/时间/在场快照」（§7.7 回看 UX）自洽。注意 FR-011 验收
原文写「新行落库（location/fic_day/present/summary）」，若按字面把收束 summary 直接写进
新行则远景语义错位一代——此歧义需确认。**不新增** `update_scene` / `soft_delete_scene`
（v1 无此需求；regenerate 撞已结算边界的限制见 §7-3）。

**domain 纯函数落点**：`fiction_time.rs`、`state_expiry.rs`（§4），触发判定与输出
normalize 放 director.rs——全部可离线单测；编排集成测试走 `infra::llm::mock::MockServer`
（`generation.rs:782+` 的成熟模式）。

## 4. 日历接线（fiction_time.rs ↔ date_label ↔ calendar_config）

- **数据来源**：结算读 `session.calendar_config`——建会话时已从 Character 复制的快照
  （`infra/storage/sessions.rs:26-55`，FR-013「日历归属与继承」），之后各自演进；
  结算只读不回写。
- **fiction_time.rs 填充内容**（全部纯函数 + 单测，BR-003）：
  - `CalendarConfig` 结构（§7.6 schema：name / months / days_per_month / day_names /
    festivals）+ `Default`（v1 默认历 = 无命名皮肤）；
  - `parse(Option<&str>) -> CalendarConfig`：None/空 → 默认历；坏 JSON → 默认历 +
    eprintln（日历是皮肤，坏了退默认不阻塞结算——与配置文件快速失败语义不同，这里
    降级无账实风险）；
  - `date_label(&CalendarConfig, fic_day, fic_part) -> String`：day 双射换算
    （day-1 → (月序, 日序) + day_names 取模 + festivals 查表命中则缀节日名）；无皮肤时
    `第{day}日·{part}`；越界回退数字形式；
  - `clamp_day(new, last)` 与 `PARTS` 六值校验（§2 字段级容错用）。
- **结算时序**：LLM 出 `fic_day/fic_part` → Rust clamp/校验 → `date_label` 派生 →
  四字段连同 location/time_note/summary/present 进 `commit_settlement`。预设历法
  （现代公历/七曜/干支/架空）与起始锚由 FR-014 开局向导切片写入 calendar_config，
  本切片只需正确消费 JSON。

## 5. 前端可见性最小集（第一期推荐：只落库，零新事件、零前端改动）

推荐**第一期只落库 + 复用既有 done 事件后前端重拉**，理由：

1. **时序已天然正确**：done 在结算后才放行（§1），前端既有收尾链路自动保证「看到终态
   时结算已在库」——`streamHub` done → `notifyTerminal`
   （`src/features/chat/streamHub.ts:146-149,109-114`）→ `ChatView.settleSession` 重拉
   `listMessages`（`src/features/chat/ChatView.tsx:210-232`）→ `onTerminal →
   refreshSessionsQuietly`（:241）。与 SEQ-001 完全同构，不引入新时序约定。
2. **没有消费方**：前端无任何 scenes API（`src/api/types.ts`/`commands.ts` 零 scene
   痕迹），`EnsemblePanel.tsx` 是 null 占位；新增事件要动 INT-001 wire + bindings 再生成
   + i18n，投入无出口。
3. **用户可见体验不缺失**：模型写的 `---` 本身已由引擎渲染成 `hr.scene` 场景线
   （`src/engine/parser.ts:20` → `src/engine/index.ts:341`，`index.test.ts:46-54`），
   第一期缺的只是「点开线看元信息」，属二期。
4. **验收可全走 Rust**：mock 网关集成测试断言 done 放行前 scenes/character_state 已
   落库（复用 `generation.rs:821-834` 的 EventLog 时序断言）+ SQL 级字段断言；
   `pnpm run check` 前端侧零变化即回归通过。

二期再做：`list_scenes` 读命令（登记 `config/ipc-command-whitelist.json` + bindings
再生成）、场景头信息条、状态面板、在场 chips（FR-010/ADR-006 manual 锁存储一并设计）。

## 7. 风险与开放问题（需用户拍板；实现切片先按推荐执行）

1. **scenes 行语义**（§3）：边界快照模型 vs FR-011 验收原文「新行含 summary」的字面
   读法，二选一，影响 `commit_settlement` 形态。**推荐：边界快照模型**。
2. **结算被用户打断后的欠账**：ADR-005 只说「可打断退出等待」。打断后是(a)留缺口、
   下次 `---` 触发时因输入携带全量状态集而自然补齐（账实部分自愈），还是(b)在会话上记
   「结算待补」标记强约束？**建议 v1 用 (a) + 文档记录**。
3. **regenerate 撞已结算边界**：旧 assistant 被整条替换后，其触发的场景行/消息归属不
   回滚（无 `soft_delete_scene` 端口）。**v1 建议接受此已知限制并记录**；要修需加端口
   语义。
4. **单条消息多道 `---`**：**v1 一次结算（取最后一道边界）**；逐边界多次结算是后续
   增强。
5. **结算模型是否随角色覆写**：INT-003/FR-009 已定「跟随主模型、专用设置项取消」；
   Character.model_config 是否也允许 `directorModel` 覆写——**建议不做**，保持配置面
   最小。
6. **重试上限与降级**：ADR-005 定了无上限，但其「再评估条件」（专用模型也频繁失败）
   何时触发、要不要加「连续 N 次失败提示 + 手动兜底按钮」，**建议一期只做日志**，二期
   看体感。
7. **在场 roster 收窄**：多角色会话数据模型（UC-002 roster、ADR-006 manual 锁存储）
   未落地，**v1 `present` 恒为 `[session.character_id]`**、输出中 enter/exit/present
   变化仅校验不扩展——确认此收窄可接受。

## 2026-09-12 裁决修订：边界快照只属于被收束的场景

> 本节为事后追加的修订记录；§3「scenes 行语义」与 §7-1 保留历史原文，不回改。

Task-03 起 recap（summary 同路径）实际落库为**双写**：`close_summary` / `close_recap`
回写上一场景行（COALESCE，None 不动既有值），同一份裁决值又**预填进新场景行**
（`NewScene.summary` / `recap`）。该预填已被 2026-09-12 裁决废除：

- **缺陷（陈旧残留）**：新行是「进行中场景」的 header，却携带上一场的裁决文本。
  第 N 次结算产出 recap → 新行 X 预填了它；第 N+1 次结算模型未产出 recap
  （`verdict.recap = None`）→ `close_recap = None` → COALESCE 不动既有值 → 行 X
  （之后作为桥场进入编年史加厚档）展示的 recap 描述的是**上一场**内容——桥场回顾
  错位；summary 同理且更持久。此外 director 结算 prompt 读 latest scene 的
  recap / summary 作为输入，也会读到这份陈旧预填。
- **修订后语义**：`build_write` 中 `NewScene.summary` / `recap` 恒 `None`——边界快照
  只属于被收束的场景。行上 summary / recap 的唯一来源 = 它自己被收束时的那次
  `close_*` 回写；`None` = 模型未产出 → 字段缺失自然省略（编年史 skip 该字段、
  桥场回退单行，既有渲染路径已覆盖）。backfill 的 COALESCE 语义保持不变。
- **顺带收益**：director 结算 prompt 读到的 latest recap 不再可能是上一场的陈旧值。
- **落点**：`services/director.rs` 的 `build_write`；存储层（`infra/storage.rs`
  `commit_settlement`、`infra/storage/scenes.rs` `backfill_close`）零行为变更。

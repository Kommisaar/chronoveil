最终方案：多角色群像 与 时间线分叉2026-09-12 · 全部决策已拍板

本文是两轮讨论的收敛产物，取代 docs/设计备忘-多角色群像.md 的待定项。决策依据：用户逐条拍板（账本 run 20260911T134930Z-292a175d decision 事件）。实施按三步依赖链，每步独立验收。

〇、核心模型一句话

角色卡库（模板）──选卡/动态造人──→ 会话实例宇宙（快照，独立演进）──手动导出──→ 模板库 └──任意分叉点──→ 新时间线（历史快照 + 当时状态，独立演进）

两条公理：① 卡是死的，人是活的——卡只做初始化模板，一切运行时身份挂在会话实例上；② 时间线是树不是链——任何历史点都可以分叉出新世界，线内规则照旧，跨线由实例隔离保证。

一、已拍板决策（9 项）

D1 模板/实例分离：角色卡 = 初始化模板；建会话时所有入选角色从卡实例化快照进会话，之后改卡不影响已开会话，实例态独立演进。v1 唯一的快照例外（日历）升格为普适规则。
D2 扮演位必选：用户必须选一张卡扮演「你」——提供用户侧设定；扮演位从卡实例化，与 LLM 扮演位同构区分（is_user 恰好 1）。
D3 Q1 生成模式：按角色逐拍独立生成（原语路线）——每个 LLM 位角色每拍各自一次调用；用户位由用户亲自输入。
D4 Q2 离场清算：不在场角色状态照常清算（遗忘 = 不再注入），不做冻结。
D5 Q4 roster 无上限：同会话角色数不设硬限；过多角色的 token/耗时代价由使用者承担，调用次数在轨迹面板明示。
D6 动态人物：会话内可随时动态创建人物（建议走导演裁决通道），只活在会话实例内；绝不自动入库，「保存为角色卡」是用户手动显式动作（实例 → 模板的手动收编）。动态人物与选卡人物同权。
D7 greeting 移除：单角色卡片式开场的遗物，已被场景式开局取代（0004 已删模板表列）；实例表不设。开场职责归场景 seed。
D8 无迁移负担：预发布无存量数据——schema 可破坏性变更，迁移只需保证全新库建到最新（AGENTS.md 已记，发布后失效）。
D9 Q5 关系键：「对XX」文本约定（key 内写目标实例名），不加列；状态表 (instance_id, key) 唯一。实施中若发现指向歧义再升级。

二、数据模型变更

现状 schema 详见 docs/报告-数据模型.html。变更三件事：

2.1 新表 character_instances（核心）

列说明
idPK。运行时角色身份的唯一标识
session_id → sessions实例必属会话
character_id → characters（可空）模板溯源：选卡实例化记卡 id；动态造人 NULL（D6）
name / persona / render_style设定快照（D1：值拷贝，改卡不回写）
is_user扮演位标记，全会话恰好 1（D2）；侧栏/统计读它
created_at / deleted_at软删惯例（ADR-009）

2.2 既有表的三处换挂

  • messages.character_id（0002 死列，从未写入）→ 激活为 instance_id；wire 的 characterId 从「命令层推导假值」变实例真值；历史消息不回填。
  • character_state.character_id + session_id → instance_id（会话隶属由实例携带）；唯一约束 (character_id, session_id, key) 简化为 (instance_id, key)；Q5 关系键走 key 文本。
  • scenes.present（JSON 数组，v1 恒 [占位]）→ 实例 id 数组，真语义。

2.3 删除与保留

  • sessions.character_id 删除（D2 的 is_user 取代）；calendar_config 快照列可留（实例化先例，或一并移入会话级配置——实施时定）。
  • characters 模板表全部列保留（greeting 0004 已删），与运行时彻底解耦。
  • llm_calls 不受影响；其 session_id 语义扩展为「时间线」（见 3.3）。

三、三步实施链（依赖严格，倒做会返工）

第 1 步会话角色实例层（地基）

做什么：迁移建 character_instances + 三处换挂 + 建会话流程改造（选卡阵容 + 扮演位 → 逐卡实例化）+ 开局向导两步选人 UI + 装配/结算/探索器按实例取人设。

验收要点：同会话 1 用户位 + N LLM 位实例共存；改卡不影响已开会话的装配输出；动态人物实例（character_id=NULL）与选卡实例同权；messages.character_id 死列消失。

风险：触全链（装配/结算/探索/wire/UI），最大单片；建议「存储+服务」与「wire+UI」两 builder 契约冻结并行。

第 2 步状态历史化（方案 A）

做什么：character_state 从 upsert 改 append-only——每次变更插新行，旧行打 superseded_at；查询语义改为「取当前生效行」（superseded_at IS NULL）；新增「取某时间点（场景 idx / 消息 id）前最后生效行」的查询。

验收要点：现有装配/结算行为不变（读「生效行」视角）；同 key 多次变更保留全链（警惕→释然→悲伤 三行都在）；时间点查询可还原「第 N 场时的状态」。

方案 B（分叉时用 LLM 重建状态）已否决：还原的是猜的不是存的。

第 3 步时间线分叉

做什么：任意场景/消息上「从此分叉」→ 新会话：拷贝锚点前全部消息/场景行（session_id 整体改写，禁止引用式偷懒）→ 每实例取「锚点前最后生效状态行」落新实例 → 分叉锚记入新会话元信息 → 分叉 UI。

三个单链假设的重审（本步核心）：

  1. scenes.idx：各线独立计数；拷贝的历史场保留原号，新线从锚点下一号长自己的场次；号在本会话内唯一（表结构天然支持），UI 标明所属时间线。
  2. BR-003「虚时绝不倒流」收窄为「单时间线内不倒流」：每条线独立虚时钟，从分叉点重新起算；跨线回退合法且正是分叉的意义。clamp_day 按会话取账本值需重审措辞与测试。
  3. 探索器隔离确认：拷贝必须彻底（消息/场景行归属切到新会话），探索器按会话过滤天然不串线；两线各自的场号列表各自正确。

验收要点：第 7 天分叉回第 3 天——新线状态是第 3 天当时值（无第 7 天才获得的东西）、虚时从第 3 天重走、原线零影响、两线轨迹面板各自独立可查。

四、与既有体系的接线

  • 结算/导演：verdict 的 state_upserts/clears 按 instance_id；动态造人建议走导演裁决（D6），裁决 schema 增新登场人物字段，与状态清算同通道；多角色逐拍生成 N 次调用，轨迹面板 kind=dialogue 天然按实例显示归属（D5 的「次数明示」由它承担）。
  • 探索器：search_history/read_scene 按会话过滤不变；命中标签随实例语义自然精确；跨线隔离由第 3 步的拷贝彻底性保证。
  • 账本面板：状态/场景史读实例；调用轨迹段（Task-28/29）不改即用；「在场：…」行展示的实例名即 roster。
  • 活动条/透明化：逐拍生成的 N 次调用按角色透出「正在以 苏鸢 的身份思考…」——透明化三部曲的自然延伸。
  • 历法/虚时：快照在会话级（FR-013 不变）；BR-003 收窄见第 3 步。

五、开放问题（实施中再裁，不阻塞立项）

  • calendar_config 快照列留 sessions 还是移会话级配置块（第 1 步实施时定）。
  • 动态造人的触发方式：纯导演自主裁决 vs 用户半自动（「给这里加个人物」指令）——倾向两者都支持，导演裁决优先。
  • 导出为卡的内容选择：原始快照 vs 快照+演化沉淀（导出 UI 时定）。
  • 分叉锚点粒度：场景级还是消息级（建议场景级起步，消息级后补）。
  • 多角色同一拍内各角色的「发言顺序」：并行生成后按什么序拼接（叙事自然序 vs roster 序，第 1 步 UI 层定）。

六、验收总纲

  1. 建会话：选「旅人（我）」+「苏鸢」「阿烬」三卡 → 三实例，is_user 恰一。
  2. 玩几拍：苏鸢、阿烬各自独立生成；轨迹面板显示每拍 N 次 dialogue 调用与归属。
  3. 导演裁决引入第四人「路人甲」（动态）→ 下一拍起 roster+1，调用次数+1 明示。
  4. 改「苏鸢」模板卡的人设 → 已开会话的苏鸢实例不变（模板/实例分离实证）。
  5. 第 2 步后：查看「苏鸢@第 3 场时的状态」——与当时装配快照一致。
  6. 第 3 步后：从第 3 场分叉 → 新线状态=当时值、虚时回第 3 天、原线零扰动、两线并行推进互不影响。
  7. 全部门禁绿：cargo / vitest / tsc / 守卫（含新表迁移专项测试）。
